# 审计报告模板（result-verification 深化材料）

按需加载。本文给出 diagnosis/ 报告的必含要素、分级标准与四类审计的报告结构。

## 1. 通用规范

本节四条规范对所有审计报告生效。

- 路径与命名：`diagnosis/<主题>_<yyMMdd>.md`（主题如 `audit_code_pipeline` / `audit_figures_vs_design` / `audit_manuscript_vs_pipeline` / `qc_<对象>` / `verify_hdd_<对象>`）。
- **只增不改**：定稿后不改写。复审另立新文件，或在文末追加“补记”章节，注明日期与触发原因；新报告生效后旧报告删除，handoff 记一行。
- 配套复现脚本：一次性脚本 `tmp_*.R` 用完即删；需留痕的复算脚本归档到根 `deprecated/diagnosis/`（README 在案），正文注明路径。
- 写作语言：先结论、后证据与可核对数值（全局规则）。

## 2. 必含六要素

报告正文按下面六项要素组织。

```markdown
# <主题>（<yyMMdd>）

- **审核日期 / 范围**：<对象文件清单，逐个列出>
- **方法**：<静态通读 / 运行时核对 / 重跑验证 / 微型 V1 复算 / 独立对照（子代理×N）>
- **对照基准**：<设计规范文件的对应节 / 图件意图 Vn / 手稿的对应节 —— 注明基准自身的版本日期>
- **结论**：<一句话总判定：通过 / 通过但有条件 / 有阻断>
- **证据锚点**：<QC 值、维度实测、锚点数值——每个判定数字附复算来源>
- **问题清单与修复落点**：<下表，带 文件:行号>
```

## 3. 问题分级

问题按影响分三级，处理时限不同。

| 级别 | 定义 | 时限 |
|---|---|---|
| **Blocker（阻断）** | 结果口径错误/错位/违反契约；下游不得采信 | 立即修，修完重审该点 |
| **Must-fix（需修）** | 不改数值但误导解读（缺注记、措辞口径、图例歧义） | 下一次迭代前 |
| **Info（信息级）** | 记录在案即可（风格、可优化点） | 不强制 |

每条问题必须能被另一个人独立复核。写清三件事：看到什么、为什么算问题、依据哪条契约或口径。

## 4. 四类审计的报告结构

四类审计各有对照重点与结论表，分述如下。

### 4.1 代码 ↔ 设计审计

逐 step 对照三样东西：设计公式链（四栏）、实现要点、实测维度与 QC sheet。结论表给每 step 一个状态：“落实 / 落实但偏差（说明）/ 未落实”。特别核对数据契约逐条：独立子情景、统一分母、行序、禁二次加权、负贡献、Baseline 恒 0。

### 4.2 图件 ↔ 设计审计

逐图对照三样东西：图件意图（insight Vn/Gn）、figN 脚本、数据契约。核查四项：数据源是否现行（非旧代）；口径是否与 output 表一致；诚实注记是否齐全并落在 figure caption，包括剔除、截断、Σ≠ 与负值；红线值是否过期。另查图面清爽：图内只留读图必需的标记，无括号解释与图底「注：…」行。结论按图分级。

### 4.3 手稿 ↔ 管线审计

逐节对照两组关系：手稿公式、设计文档公式链、代码变量映射三者之间；手稿数值与 output 表实测之间。同时查手稿**内部自洽**。实战曾发现：手稿某节的分母定义与另一节矛盾，证据指向改手稿，而非改代码。分歧项逐条列“手稿 / 代码 / 设计文档”三方表述与裁决建议。

### 4.4 产物 ↔ 产物审计

做上游 sheet 与下游汇总的传递核对：行和、列和、总量逐值比对，记录 max|diff| 实测值。覆盖差异要写明成因，如 1 位小数舍入 0.0499 类。

## 6. 审计自身的验证

审计本身也要接受检验。

- 抽 1 至 2 条“通过”结论做反向复核，换个方法再核一次。审计也有错的时候。
- 审计基准过期的风险：对照物（设计文档/意图清单）自身要注明版本日期。基准已变而审计未更新时，补记声明。
- 曾有整套审计因“未正确识别研究意图”而整体作废。**审计前先读根 AGENTS.md 与研究问题**，不要拿着自己的想象当基准。
