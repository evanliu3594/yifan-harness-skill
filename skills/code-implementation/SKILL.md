# Code Implementation：代码落地

## Overview

把设计（research-design）翻译成可复跑的脚本。核心纪律是 **HDD（假设驱动开发）**：先提出可证伪的假设与验证方式，再动手实现。实现后以验证结果收口。脚本是唯一事实源，产物永远可由脚本重生成。

**REQUIRED SUB-SKILL**：`hdd`，其中定义了六步流程 HT→PT→AT Design→DEV→AT Run→E2E。本技能规定 HDD 在研究代码场景的入口判定与强制产物。流程细节以 hdd 为准。

## Iron Law

以下四条是硬约束，写代码前逐条对照。

1. **无假设不动手。** 任何代码实现或改动前，先声明假设。假设要写清三件事：预期结果是什么、如何验证、看到什么则假设为假。
2. **无验收标准不开发。** 写代码之前先写 AT（验收用例）：输入/操作 → 预期数值或性质。AT 必须在 DEV 之前锁定。不允许事后调整标准去适配结果。
3. **QC 不过不收口。** 脚本末尾的契约检查（stopifnot/锚点/QC）不通过，不得宣称完成。“看起来对”不算对。
4. **改产物必改脚本。** 禁止手改任何生成物（xlsx/rds/png）。要改结果就改脚本重跑。

## When to Use

以下情况使用本技能。

- 实现新的计算步骤（stepN）、图件脚本（figN）、公共资源（_common/）。
- 修改现有脚本中影响结果的任何逻辑。
- 修 bug、优化、重构、换依赖版本。

本技能不适用两类工作。一是纯手稿文字编辑（manuscript-writing）。二是不改代码的数据核对（result-verification）。

项目级实现时，若 G1 尚未通过，先回 research-design 补设计，不直接开工。未通过指没有设计文档、口径未登记。快算与小改按 research-design 的级别规则执行，不要拉长成项目级流程。

## HDD 流程分流（先判定，再动手）

先判定走哪种流程，再动手。判据见下表。

| 判定 | 走法 |
|---|---|
| 诊断/debug、优化/选型、架构/配置变更、**结果不确定**的改动 | **完整 HDD**：资源映射 → 分层定位 → HT（假设+先验+证据等级，诊断须达 V1/V2）→ PT（方案验证）→ AT Design → DEV → AT Run → E2E |
| 用户已拍板、预期结果已知的机械改动（改文案、单位换算、重命名、按既定模板加图） | **简化 HDD**：执行前声明“预期不变/预期值”，执行后核对一遍即可 |

判定不了算哪种 → 按完整 HDD。完整 HDD 的证据等级（V1 现场复现 … V5 纯推理不算证据）与回退路径见 `hdd` 技能。

## 实现规范

本节定脚本命名、头部契约与实现要点。

### 脚本命名与角色

脚本按角色命名，规则如下。

- `stepN_描述.R`：管线计算（step0 = 前置准备/对齐，不计入计算管线）。
- `figN_名称.R` / `SI_Fig_S*.R`：图件，每图一脚本，可独立运行，不占计算 step。
- `_common_proc.R` / `_fig_common.R`：常量 + 助手函数。各脚本头部 `source()` 复用。函数不加载包，由调用方加载。
- 单一职责：一个脚本一件事。连接表生成类脚本一对一拆分。

### 脚本头部契约（每个脚本必须写）

每个脚本头部按下面的注释模板逐项写全。

```r
# <文件名> —— <角色一句话>（<日期>，HDD 流程落地）
# 方法：<核心公式/口径要点，与设计文档公式编号对应>
# 输入：<文件路径（正则模式） + sheet>
# 输出：<文件路径 + sheet 清单>
# 运行: Rscript --vanilla R/<文件名>（工作目录 = 项目根）
```

### 实现要点（防错基线）

以下六条是实现时的防错基线。

- **环境**：固定解释器全路径（如 `Rscript --vanilla`）。语言版本与包版本登记在根 `AGENTS.md` 的「基本规则（环境）」条或项目环境规范文件。脚本末尾调用 `sessionInfo()`。
- **输入**：用 `latest_file()` 按正则取日期最新一份。读入后立即 `stopifnot` 维度与行序契约；契约来自设计的维度速查表。
- **产物**：写到规定目录，文件名带 `<yyMMdd>` 后缀。结果表 xlsx 带 `notes`（口径注记）与 `script`（生成脚本）sheet。
- **风格**：遵循 `yifan-r-code-style`（R；其他语言遵循项目登记的风格基线）。
- **跨源名称匹配**：必须经持久化连接表（join_*）对齐，禁止想当然按字符串匹配。反例：United States ≠ United States of America。连接表生成一次后复用。
- **已知陷阱登记**：项目特有的坑记入目录 `AGENTS.md` 的技术要点节（≤3 行/条），或按需放进专门规范文件。典型例子：栅格行主序、dplyr 掩码裸名引用、物种显式映射而非列序表。新脚本实现前通读。

脚本骨架（step/fig/公共资源）、AT 用例写法与修 bug 最小闭环见 [references/script-templates.md](references/script-templates.md)。

### AT Run 与收口

AT 逐条跑完并核对通过，才能进入收口。

- 逐条执行 AT Design 的用例，记录“预期 vs 实际”（带数值）。
- QC/锚点全过 → E2E（用户验收）。之后做收尾检查：handoff 留痕、目录 `README.md` 清单更新、recipe 归档与过时结果删除。
- 任何一条不过 → 回 DEV 修复。发现假设本身错了 → 回 HT，不得在错误假设上调方案。

## Red Flags — 立即停下

出现下列任一情况，立即停下。

- 代码里出现了设计文档没有的口径决定 → 停，回 research-design 拍板。
- QC 不过想“先注释掉检查继续跑” → 禁止；查根因（完整 HDD 的 HT）。
- 测试通过得太顺利（AT 全部一次通过且无任何意外） → 怀疑 AT 写松了，加一条更强的不变量再跑。
- 手头改产物文件比改脚本“快” → 禁止，永远改脚本。
- 复用一段不知道为什么能跑的代码 → 先弄清假设（不懂的代码 = 未验证的假设）。

## 常见合理化（都是借口）

以下说法都是借口，不能当作省流程的理由。

| 借口 | 现实 |
|---|---|
| “先把代码写完再补验证” | 那是事后为结果找理由；AT 必须先锁标准 |
| “QC 阈值太严了，放宽一点就过” | 阈值是契约；要改阈值必须给出证据并过确认 |
| “这个小数值差只是浮点误差” | 先量化（<1e-9?），再说话；不量化不开口 |
| “这个改动很简单，不用走 HDD” | 简单是判定的结论不是借口；机械改动也须声明预期并核对 |
| “反正后面审计会查” | 审计查的是你留下的证据链；没跑过 QC 的代码审计也救不了 |

## Verification Checklist（放行进入 result-verification）

放行前逐条勾选，全部勾选才能进入 result-verification。

- [ ] HDD 分流判定成文（完整/简化 + 理由）；完整流程的 HT/PT 结论有证据等级
- [ ] AT Design 用例在 DEV 前锁定；AT Run 逐条“预期 vs 实际”通过
- [ ] 脚本头部契约完整（方法/输入/输出/运行方式）
- [ ] 输入读取用 latest_file + stopifnot 维度/行序契约
- [ ] 产物落对目录、带日期后缀、含 notes/script 自解释信息
- [ ] 全程未写 data/raw/、未手改任何既有产物
- [ ] 设计文档的公式链已回填脚本落地行号（公式↔代码对应保持同步）
- [ ] handoff 已留痕（收口文档已定稿）；目录 `README.md` 清单已更新；recipe 已归档、过时结果已删除

全部勾选 → 进入 result-verification 做独立核验；任一未勾 → 不放行。
