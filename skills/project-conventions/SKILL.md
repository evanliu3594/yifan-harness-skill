# Project Conventions：项目底座

## Overview

研究项目必须有**单一事实源**，用它承载约束与记忆。单一事实源按注入方式分三层：`AGENTS.md` 路标（每会话注入）、专门规范文件（按需加载）、各目录 `README.md` 信息表（按需加载），时间线仍写 `handoff/`。其他阶段技能开工前，先读本技能确立的约定，再读最新一份交接。收口后，按本技能留痕交接。

## Iron Law

以下各条为硬约束。

1. **没有项目总纲不开工。** 项目根无 AGENTS.md 时，先用 templates/ 初始化。骨架建好后，再进入任何实质工作。
2. **每次改动必须留痕，会话收口必须交接。** 留痕载体 = 当次 handoff 文档。开工即建，随做随记；改动落盘未记入 = 任务未完成。会话收口补全定稿。项目有 git 时，收口 handoff 必须提交入库；未入库 = 任务未完成。
3. **只归档 recipe；过时的结果直接删除。** recipe 指产出生产结果的计算脚本、管线配置与绘图脚本。它移入根 `deprecated/<原目录>/`，在该目录 README 登记；被取代的中间数据、结果表、图件、报告与旧文档直接删除，不归档，只在当次 handoff 记一行（文件名 / 删除日期 / 原因 / 再生依据）。一次性探针、`tmp_*`、备份副本用完即删。判据：它造结果，还是它就是结果。造结果的归档，结果删除。
4. **先算注入预算，再决定写哪。** `AGENTS.md` 每会话注入，总量有硬上限（DSH 实测 65,536 字节），超了静默截断尾部。写之前按 `references/doc-architecture.md` 的「注入预算模型」节算一遍。
5. **口径歧义先听后问，回放确认。** 需求不明确、口径有歧义、存在多个可选方案时，先问目标，再回放理解，最后确认口径。规程见“需求确认协议”。不得自行假设后继续。也不得把未说出口的默认值当成已确认。

## When to Use

本技能在以下情形激活。

- 新研究项目立项，或老项目首次纳入本框架（初始化骨架）。
- 任何阶段技能（research-design / code-implementation / result-verification / data-visualization / manuscript-writing）开工前：检查总纲是否存在且现行。
- 改动完成后的收尾留痕。
- 不确定文件去向、要废弃旧产物、或需要升级口径决策时。

不适用：纯问答（不改任何文件）。

## 文档分层体系（路标 / 规范 / 信息表）

**三层分工：路标 / 规范 / 信息表**。`AGENTS.md` 每会话注入、有总量上限，只写"每轮决策都要用"的内容；细节下沉到按需文件。时间线全部写入 `handoff/`。

| 层 | 文件 | 内容 | 上限 | 维护时机 |
|---|---|---|---|---|
| 路标 | `AGENTS.md`（根） | 项目定位 / **已拍板口径** / 硬规则（必须与禁止）/ 指向表 | ≤9 KB | 口径拍板、职责变化、约束增删时 |
| 路标 | `<dir>/AGENTS.md`（一级目录） | 本目录定位 / 必守 2–3 条（含后果一句）/ 去哪查表 | ≤1.5 KB | 本目录硬规则变化时 |
| 规范 | 专门文件（如 `R/_CALCULATION-ARCHITECTURE.md`、`R/_QUALITY-CONTROL.md`） | 公式、契约、QC 体系、口径细节、目录间关系 | ≤30 KB/件 | 方法或口径变化时 |
| 信息表 | `<dir>/README.md` | **本目录文件清单**（一行一文件）/ 子目录一句话 | ≤20 KB/件 | 增删或归档文件时 |
| 时间线 | `handoff/`（一份一文档） | 会话交接记录 | — | 开工即建、收口定稿（强制） |

**关键判据：文件清单属于 `README.md`，不属于 `AGENTS.md`。** 旧的"目录级 AGENTS 写文件清单"模型会让注入体积随文件数线性增长，实测必然超预算。

总纲模板见 `templates/AGENTS_root_template.md`；目录路标见 `templates/AGENTS_subdir_template.md`；信息表见 `templates/README_perdir_template.md`；交接见 `templates/handoff_template.md`。上限、归属判定、迁移七步、批量改写三坑见 [references/doc-architecture.md](references/doc-architecture.md)。**初始化分两路**。空仓库从模板建骨架，文档先行。已有内容仓库必须先考古：现状盘点 → 与用户对齐 → 登记现状。禁止拿模板覆盖现实。遇旧 AGENTS.md/CLAUDE.md，按"验证后继承"处置，不删掉重来。完整程序见 [references/init-procedures.md](references/init-procedures.md)。

分层检查如下。在根总纲里写"某日做了某事"，停下；这类内容属于当次 handoff。在 handoff 里写规则，停下；规则属于总纲。**索引里写正文摘要，停下**；索引行 = 文件名 + 一句话 +（口径/判定类才加）一句结论，整行 ≤120 字符。**README 里出现"见 <该文件自己>"，停下**；那是自指，必然是错的。同一约定只保留一处正文，别处留指针。

### 经验与陷阱的归置（不设 EXPERIENCE.md）

本小节规定经验往哪里放。

经验是原料，不是库。不新增独立经验文件。它会无限增长，且无晋升纪律（坟场化）。它还会与规则双权威漂移，并占每会话常驻上下文。经验走**晋升管线**。流程是：事故发生 → 当次 handoff 留痕 → **会再咬人的才晋升**。审计发现另立 diagnosis 报告。晋升去向如下：

- **可复用约束** → 写入对应 AGENTS.md 成为规则，附一行反面案例（“禁 X（YYMMDD 曾犯：<症状>，已修复）”）；
- **已验证的技术事实**（工具行为、数据格式陷阱）→ 目录 `AGENTS.md` 的技术要点节（≤3 行/条），或按需放进专门规范文件；
- **一次性教训**（无未来适用性）→ 只留当次 handoff；
- **跨项目通用** → 晋升出项目，成为技能。

细则（晋升判据、规则带疤式样、条目退役、暂存豁免）见 [references/memory-architecture.md](references/memory-architecture.md)。

## 目录契约（先判型，再套契约）

目录契约按**项目原型**分型。下表是默认原型 **A 数据分析**（既有观测数据 → 分析 → 手稿）的契约。初始化第一步先判型。数据由程序生成 → B 仿真。交付可安装的包 → C。纯文字交付 → D 手稿/综述。持续运行的应用 → E。判不了型时，走需求确认协议：

| 原型 | 交付物特征 | 契约 |
|---|---|---|
| A 数据分析（默认） | 实证结果表 + 图 + 手稿 | 下表 |
| B 仿真/方法研究 | 模拟证据（Monte Carlo、功效分析、方法比较） | [archetypes.md](references/archetypes.md) 的 B 型节 |
| C 软件包/工具库 | 可安装复用的包 | archetypes.md 的 C 型节 |
| D 手稿/综述写作 | 文字与文献综合，无新数据分析 | archetypes.md 的 D 型节 |
| E 应用/仪表盘 | 持续运行的交互应用 | archetypes.md 的 E 型节 |

A 型目录速查：

| 目录 | 职责 | 写入规则 |
|---|---|---|
| `data/raw/`（及外部只读源） | 原始数据 | **只读**，任何脚本不得写入 |
| `data/proc/` | 派生数据、中间文件、连接表 | 由 step 脚本生成，日期后缀 |
| `output/` | 最终结果表 | 只由 step/fig 脚本写，日期后缀 |
| `pics/` | 图件 | 只由 fig 脚本写，日期后缀 |
| `R/`（或 `code/`） | 全部分析脚本 | stepN / figN 命名；唯一事实源 |
| `diagnosis/` | 自检/审计报告 + 配套验证材料 | markdown，`<主题>_<yyMMdd>.md`，**只增不改** |
| `insight/` | EDA 洞察与可视化建议 | markdown + 复算脚本，只读分析 |
| paper/（或 scripts/） | 论文手稿、方法描述、汇报材料 | **产出层**：只写交付件，不放规范 |
| `<dir>/README.md` | 本目录文件信息表 | 只记文件名、一句话内容、生成脚本；不写规范与沿革 |
| `deprecated/`（根，唯一归档根） | 被取代的 recipe（计算脚本与管线配置），按原所在目录分 `deprecated/<原目录>/` | 只归档 recipe；过时数据、结果与旧文档直接删除，只在 handoff 记一行 |

A 型细则见 [references/directory-contract.md](references/directory-contract.md)。细则涵盖跨目录文件流、日期后缀规则、例外处置。各原型目录契约、跨原型不变层、根总纲按原型微调，见 [references/archetypes.md](references/archetypes.md)。

## handoff 交接记录协议

时间线载体已由 HISTORY.md 单文件升级为 `handoff/` 交接目录。改造自 mattpocock/skills 的 handoff 模式。**一份交接文档 = 一个工作会话的收口快照**。下一个 agent（或三天后的你）不带上下文，也能接续。

**时机与命名**

- 开工即建当次文档 `handoff/<yyMMdd>_<主题>.md`，随做随记。同日多份靠主题区分；仍冲突时加 `-HHmm`。会话收口时补全定稿。
- 定稿后**只增不改**。勘误写在下一份 handoff 的“更正”里，不回改旧文档。
- 文件名领衔日期是有意设计。handoff 是编年记录而非代次产物。按文件名排序即时间序，不适用 `latest_file()` 模式。

**文档结构**（模板见 `templates/handoff_template.md`）

1. **元信息**：收口时间、上一份交接指针、下一会话焦点（用户指定则照录，并据此裁剪详略）；
2. **改动清单**：每改动一行——动作 / 动机 / 影响面；
3. **验证结果**：QC/锚点/审计结果，带数值。未验证的如实标注“未验证”；
4. **口径变化**：无则写“无”；有则新旧对照，注明根 `AGENTS.md` 的「已拍板口径」已同步；
5. **遗留问题与下一步**：缺口、未收口事项、风险；
6. **建议技能**：下一会话应调用的技能清单，各一句理由；
7. **指针**：相关产物 / diagnosis 报告 / commit 的路径或哈希。

三条内容纪律。**引用而不复制**：不重述 AGENTS.md、diagnosis 报告、代码 diff 里已有的内容。给路径或哈希即可。**敏感信息一律脱敏**：API key、口令、个人敏感数据不落 handoff。凭据只留占位与指针。**写不出口径影响或验证结果 = 改动尚未收口**，先回 result-verification。

**Git 纪律（有 git 的项目强制）**

- 收口 handoff **必须提交进版本库**。它与本次改动同一提交，或紧随其后的独立提交。有 git 而收口 handoff 未入库 = 任务未完成。
- `.gitignore` 不得排除 `handoff/`。handoff 有脱敏纪律，本身可安全入库。
- 项目无 git 时，落盘即生效。本框架不依赖 git，但依赖 handoff。

**接续纪律**

- 下一会话开工先读根总纲，再读 `handoff/` 最新一份（文件名排序最后一份），然后定位阶段。
- 接续者发现 handoff 记载与现实冲突时，以现实为准。冲突点记入下一份 handoff。

**存量迁移**：升级前已有 `HISTORY.md` 的项目，把关键节点摘入首份 handoff 的「指针」节，原文件删除。迁移动作记入首份 handoff，此后旧文件不再维护。

## 变更之后：全项目同步

任何**变更**之后，全项目的非归档件必须在同一轮回到同一代次与同一口径。这是顶层规则，不是可选步骤。

**五类触发**（任一命中即触发全量同步）：计算/数据（重跑、换源、换批次）；**口径/定义**（定义、单位、时间窗、边界、纳入排除、判定标准与容差）；结论（判定翻转、订正、撤回）；规划/结构（目录、命名、步骤顺序、交付清单）；目标/范围。
**第 2 类最易被漏**：口径变了而数字可能一个都没变，于是没人去动正文，但正文的事实陈述已经错了。判定标准与容差也算口径。

**边界三问**（每件都问）：这是冻结件吗（是 → 不改，但索引标 `superseded` 并给现行件指针）？被现行文件引用吗（是 → 改引用目标，或标注"引用旧版及原因"）？它是索引/导航/对照表吗（是 → **必须更新**，哪怕它看起来像文档）？

**十步**：诊断类型 → 立变更单 → 列影响面清单（逐目录实际看，不凭记忆）→ 定代次与现行指针 → 执行变更 → 更新锚点表 → 三通道清扫（文件名与代次 / 数字 / 旧表述）→ 重打交付件 → 收口登记（AGENTS、README、索引全部更新，未同步项显式登记）→ 逻辑对读（摘要 ↔ 结论 ↔ 图注 ↔ 变更单）。

**任何一步没做，写进"未完成"，不要省掉。** 完整规程（四种不一致、影响面八层清单、四类锚点表、十二类失败模式、收口定义 DoD）见 skill `downstream-sync`；本框架只强制"变更必同步"这一条与它的收口登记要求。

## 需求确认协议：先听目标，再问口径

本节规定何时问、怎么问。

触发条件（任一）：

- 需求不明确，存在多种解读；
- 研究目标或“为什么做”没有说过；
- 口径有歧义，包括定义、分母、边界、单位、时间基准；
- 存在多个可选方案，取舍影响结果；
- 要改动**已拍板口径**，即总纲登记过的决策。

先分诊，再决定怎么问。目标不清时，先问一个开放问题。听完回放 200 至 300 字，把猜测标注清楚。用户确认后，再列口径点。目标清楚、口径点离散时，一次列全口径点，避免来回。

执行方式如下。

1. 目标层用开放问题。口径层用选项清单，通常 2 至 3 个。
2. 每项给出影响说明、推荐项及理由。影响说明写清对结果和工作量的影响。
3. 回放理解，把用户原话和你的猜测分开。猜测要能被用户一句话纠正。
4. 得到明确答复后才推进。答复只算批准你展示过的内容；未成文的口径不算批准。

代理决策的规则只有一条。用户没有表态、由你决定的技术选择，必须说出口。例如“我默认用 X，理由是 Y；不同意就换”。代理决定还要登记进设计文档。没说出口的默认值等于没有确认。

反面案例：自行假设“应该是这个意思”后直接实现，结果口径整体返工。用户已明确拍板、预期结果已知的机械改动不需要访谈，例如改文案、单位换算、重命名。这类改动执行前后仍须声明“预期不变”或“预期值”，并核对一遍。

## 写作语言（全局，所有交付物生效）

以下三条对所有交付物生效。

- 去除矫饰性表达。用直白、朴素、准确的话阐述，像对外行说话。
- **先结论、后证据**。证据须带可核对数值。
- 不用“大概、可能、应该没问题”敷衍判定。要么给出证据，要么明说“未验证”。

## 归档与删除协议

分三类，判据是**它造结果，还是它就是结果**。造结果的（recipe）归档；结果本身过时即删。

**recipe（归档）**：产出生产结果的脚本与配置——stepN / figN 脚本、公共函数、管线配置、QC 与复算脚本，含被取代的旧版本。

- 一律移入**根** `deprecated/<原目录>/`，保持原相对路径；子目录下不建 `deprecated/`。这是唯一的归档根。
- 在该段 README 记录：文件名 | 归档日期 | 原因 | 被谁取代。归档件仍可只读复跑；修正失效路径须在 README 记录，不改原逻辑。
- 现行清单里对应的行改为“已废弃 → 见 `deprecated/<原目录>/`”，防止误引用。

**过时的结果与旧文档（直接删除，不归档）**：被取代的中间数据（`data/proc/` 旧代）、旧结果表（`output/`）、旧图件（`pics/`）、被取代的报告、旧版 `AGENTS.md` 与 `README.md`。

- 直接删除，`deprecated/` 不收它们。删除动作在当次 handoff 记一行：文件名 | 删除日期 | 原因 | 取代者或再生依据。
- 删前过“删后能否再生”门槛：recipe 已归档、输入仍在（原始数据只读），才可删。recipe 补不出的，结果原地标注并请用户拍板，不静默删。
- 目录 `README.md` 清单同步删行，不留失效占位；留痕只在 handoff。

**临时件（用完即删）**：一次性探针、`tmp_*`、备份副本、试探脚本。生产链路里被取代的中间数据属上一类，删除要留痕。

- 不进归档，不在清单登记。迁移前留的回退点属临时件：验证通过后删除，但在交接里写明“回退点位置”。

## Verification Checklist

逐项过一遍，全部满足才算本技能收口：

- [ ] 项目根有 `AGENTS.md` 总纲，且不包含历史进度堆叠
- [ ] **注入预算已核算**：Σ(`AGENTS.md`) 未超上限并留出余量，数字记在交接里
- [ ] 每个使用中的目录有 `AGENTS.md` **路标**（定位 / 必守 / 去哪查），≤1.5 KB，**不含文件清单**
- [ ] 每个使用中的目录有 `README.md` **信息表**（子目录 + 文件清单），**不含规范与沿革**
- [ ] 索引行全部 ≤120 字符，索引里没有正文摘要
- [ ] `README.md` 无自指；活文档无旧章节号引用（跨文件引用一律按节名）
