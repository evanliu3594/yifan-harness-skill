# 初始化程序：空仓库（greenfield）与已有内容仓库（brownfield）

按需加载。两种仓库都用 project-conventions 技能作入口。最终产物都是同一套文档体系（`AGENTS.md` 路标 + 专门规范文件 + 各目录 `README.md` 信息表）。根本差别在**文档与代码的时序**：空仓库文档先行，从模板生长；已有仓库文档追认现实，先考古再建体系。

共同前提（两种路径都遵守）：原始数据只读；只归档 recipe，过时结果直接删除；口径有歧义先听后问（需求确认协议）。初始化过程本身要记入首份 handoff 交接文档。

---

## A. 空仓库（无代码、无结果，通常只有原始数据或什么都没有）

**原则：文档先行、随决策随记。** AGENTS.md 不是写完代码再补的课，每个决策落地时同步登记。模板即清单：模板里的占位段落就是“这个项目终将要做出的决策”；空着的段落 = 还没拍板的口径。

### 步骤

六步：判型 → 建骨架 → 拍板环境与规则 → 进入 research-design → 进入 code-implementation → 从 G1 起走全链。

1. **判型**（先于一切建目录动作）：依据 [archetypes.md](archetypes.md) 分型表，按交付物判定项目原型。原型分五类：A 数据分析 / B 仿真·方法研究 / C 软件包 / D 手稿·综述 / E 应用·仪表盘。判定不了或混合型 → 需求确认协议：先听后问，回放确认。判型成本分钟级，判错的返工是整套目录。
2. **建骨架**（templates/ 一套复制过去）：
   - `AGENTS_root_template.md` → 项目根 `AGENTS.md`。先填「研究问题与目标」与意图基线：先问目标，回放确认；问题写不清不进下一步。
   - `README_perdir_template.md` → 各目录 `README.md`。只放子目录表与文件清单；规范与沿革不进。`AGENTS_subdir_template.md` → 各目录 `AGENTS.md` 路标（定位 / 必守 / 指向）。
   - 按**所选原型**的目录契约建目录。A 型即 `data/raw`、`data/proc`、`output`、`pics`、`R/`（或项目语言的代码目录）、`diagnosis/`、`insight/`、`scripts/`。其余原型见 archetypes.md 对应节。每个目录各放一份 `AGENTS.md` 路标与 `README.md` 信息表，初期很薄：定位、必守、指向 + 文件清单。
   - `handoff_template.md` → `handoff/<yyMMdd>_init.md`。首份交接写“项目初始化（骨架建立，原型判定为 X）”。项目有 git 时，连同骨架一并提交入库。
3. **拍板环境与规则**（根 `AGENTS.md` 的「基本规则」）：语言与版本、解释器调用方式、风格基线（如 `yifan-r-code-style`）、跨源匹配策略（连接表持久化 + 复用）。以上各项逐项向用户确认。
4. **进入 research-design**（初始化默认项目级）：先做设计对话。对话三步：开放问 → 回放定稿进根 `AGENTS.md` 的「研究问题与目标」 → 执行选择归属。再依次完成：顶层实验设计 → 口径清单逐项拍板（登记根 `AGENTS.md` 的「已拍板口径」，代理决定登记「代理决策」）→ 公式链 → DAG + 维度速查 → 数据契约 → 缺口表 → 复现者检查。**设计产物写进项目文档体系**：根 `AGENTS.md` 的方案概要 + `R/_CALCULATION-ARCHITECTURE.md` 的公式链、DAG、维度、契约与缺口。不另立游离文档。
5. **进入 code-implementation**：通常从 step0 起步。第一个脚本往往是**连接表/对齐**（跨数据源的名称桥），不是计算本身。
6. **从 G1 闸门起正常走全链**。每个脚本诞生时，即在目录 `README.md` 清单登记一行。清单随建随记，不要攒。

### 要点

- 目录级 `README.md` 是活的。文件清单从 1 行长到 N 行；每增、删或归档一个文件，同步更新。`AGENTS.md` 只放定位、必守与指向，**不随文件增减而变**。
- 初始化本身很快，骨架分钟级。真正的工期在第 4 步设计拍板。不要为了“快点跑起来”跳过它，这是 G1 闸门存在的理由。
- 判型依据（交付物）写进首份 handoff 备复核。混合型的主副挂靠关系登记根 `AGENTS.md` 的「目录结构」。

## B. 已有内容仓库（有代码/数据/结果，但没有本框架的文档体系，或文档已失真）

**第一原则：AGENTS.md 描述现状，不描述理想。每一条都要有证据。** 最大的风险是凭印象写文档：那是把 V5（纯推理）当事实写进总纲，后续所有阶段都建在错误前提上。同样的教训：整套审计曾因“未正确识别研究意图”而整体作废。

**第二原则：只写文档，不改代码。** 初始化不是重构机会。发现代码问题记入缺口或诊断，修复是后续独立任务，各自走 HDD。

对“已有部分文档但失真”的中间态：旧文档的每一条要么被证据支持，要么标注“待核”。**不信旧文档的未验证断言**（同手稿写作纪律：引用没核过的数 = 审计债）。

### 步骤

六步：冻结盘点 → 考古 → 与用户对齐 → 建体系 → 补验证债 → 定位当前阶段。

**0. 冻结与盘点（只读，不改任何文件）**

- 文件树全量清点：脚本 / 数据 / 结果 / 图 / 既有文档，按目录归类。
- 识别**事实上的管线**：`source()` 调用链、脚本的读写文件模式、文件名日期后缀。据此草绘 de facto DAG。
- 标记疑似废弃：旧日期代、`_old`/`_legacy`/重复 stem、无下游引用的孤儿产物。**只标记，不动。**

**1. 考古（报告落 `diagnosis/`）**

- 逐脚本：读什么、写什么、口径是什么。先静态通读；能跑的就跑一遍，做运行时核对（V1/V2 证据）。跑不了的写明原因，其结论只能标“静态推断，待运行验证”（V3 至 V4）。
- 产物盘点：各表维度、行序、单位、日期代次。标出哪些被下游实际引用，即事实上的现行。
- 汇总为 `diagnosis/onboard_inventory_<yyMMdd>.md`：管线图 + 产物清单 + 口径发现 + **不确定性清单**（每条标证据等级）。

**2. 与用户对齐（需求确认协议的重头戏：先汇报并回放考古结论，口径点一次列清）**

- 汇报考古结论：管线图、现行产物清单、发现的口径点与歧义。
- 逐项确认三件事。第一，哪些产物现行、哪些废弃，拍板后才处置：结果删除，脚本归档。第二，**隐含口径显性化**：代码里实际执行的口径，用户认不认。第三，命名约定沿用还是迁移。
- 用户确认的口径升级为根 AGENTS.md 的“已拍板口径”首批条目。

**3. 建体系（写入“描述现状”的文档）**

- 根 AGENTS.md：研究问题与意图基线（用户口径）、数据源、管线概要、已拍板口径表、代理决策表、基本规则。基本规则**前瞻性**采用本框架规则，此后才受其约束。
- 目录级 `README.md`：文件清单，每行三态标注（现行 / 已删，脚本见 `deprecated/<原目录>/` / 待确认）。目录级 `AGENTS.md` 只登记定位、必守与指向。
- 首份 handoff（`<yyMMdd>_onboard.md`）：“纳入 yifan-harness-skill 框架”，并指向考古报告。
- 存量 `HISTORY.md`（若有）：关键节点摘入首份 handoff，原文件删除。新条目从首份 handoff 起走交接体系。
- 确认废弃的：脚本与配置移入根 `deprecated/<原目录>/`，在该段 README 记录；其结果与旧文档删除，handoff 各记一行。存疑的原地标注，不动。临时件（`tmp_*`、一次性探针、备份副本）用完即删。

**4. 补验证债（渐进，不追求一次补齐）**

- 存量代码大概率缺 QC/锚点。两条增量路径：
  - **随改动补**：下次要动的脚本本来就要走 HDD，AT/QC 顺手补在该脚本上；
  - **关键数优先**：会进手稿的 headline 数字先补锚点或交叉核对，即对账表的最小集。
- 已知缺口进缺口表，分“待实现 / 数据方法固有”。

**5. 定位当前阶段，进入正常流程**

- 项目实际处于哪一段（往往在 ③ 或 ④），闸门从实际位置起算。此后按 docs/workflow.md 的闸门与回退执行。

### 旧 AGENTS.md / CLAUDE.md 的处置（验证后继承，不删掉重来）

**定位：旧文档既不是事实，也不是废纸，而是“待验证的断言集”。** 其中“为什么”类内容（拍板口径、术语定稿、数据契约、设计动机、坑的记录）是代码与产物里挖不到的资产。删了就永久丢失。

三种错误做法，每种都有真实代价：

- **照单全收**：错误断言原样进新体系，比没有文档更糟（后人会信它）；
- **不验证就删掉重来**：丢失意图资产，旧文档里的口径与动机无法复原；
- **无视并存**：新旧两套文档漂移，agent 读到哪套看运气。AGENTS.md 与 CLAUDE.md 各说一套是常见病。

正确流程（并入上面步骤 1 至 3 执行）：

1. **文档盘点**：列全 agent 相关文档（根/子目录 `AGENTS.md`、各目录 `README.md`、规范文件、CLAUDE.md、GEMINI.md、.cursorrules 等）。记录各文件最后修改时间与最近代码改动时间，**文档旧于代码 = 失真信号**。多份文档并存时先做 diff，**分歧点清单 = 待确认的口径/事实冲突**，逐条走验证。

2. **断言提取与逐条验证**（旧文档 = 考古的一手材料，验证方式与产物对证相同）：

   | 断言类型 | 验证方式 | 处置 |
   |---|---|---|
   | 管线/口径/维度描述 | 对照代码与产物实测（能跑则跑） | ✅ 支持则继承；⚠️ 冲突则问用户（证据指向改文档还是改代码） |
   | 拍板口径、术语定稿 | 问用户确认仍然有效 | 继承进根 `AGENTS.md` 的「已拍板口径」表，补登记日期 |
   | 规则/约定 | 判断是否仍适用于现状 | 适用并入根 `AGENTS.md` 的「基本规则」；不适用剔除并在 handoff 留痕 |
   | 文件清单 | 对照文件系统逐行核 | 失效行剔除，按三态（现行/已删/待确认）重写 |
   | 历史/动机/“为什么”记录 | 无需验证（本就是史料） | 摘入考古报告附录或首份 handoff，原文件删除 |

3. **文件层面处置**：本框架以 `AGENTS.md` 为跨工具的权威入口，内容按三层拆分（路标 / 规范 / 信息表）。AGENTS.md 是开放规范，多工具通用。
   - 旧 AGENTS.md：内容按验证结果重构写入。这是**维护**，不是删除重来。内容继承完毕后旧文件删除，handoff 记一行（来源、继承 n 条、剔除 m 条）；有 git 时旧版本在提交历史里可查。
   - CLAUDE.md：若仍在用会读取它的工具（Claude Code 等）→ 保留为**兼容垫片**。正文缩为一行指针“遵循本目录 AGENTS.md”。单一事实源，杜绝两套漂移。不再使用该类工具 → 删除。**用哪些工具是用户决策，先问再动。**
   - 子目录级旧 AGENTS.md 同样走断言验证，不豁免。
4. **留痕**：首份 handoff 记“文档体系迁移”。来源文件、处置方式（继承/垫片/删除）、验证统计（继承 n 条 / 剔除 m 条 / 待核 k 条）逐项写明。

**什么时候才接近“重写”**：逐条验证后大面积失效，如旧文档描述的是已被整套取代的旧管线。重写是**验证的结论**，不是默认动作。即便如此，旧文件在内容继承完毕后删除，handoff 记一行。

### 反模式（每条都有真实代价）

下表每条都对应一次真实代价，动手前先对照。

| 反模式 | 为什么错 |
|---|---|
| 拿模板直接覆盖写一份“理想总纲” | 文档与现实两张皮，比没有文档更糟（后人会信它） |
| 初始化顺手“清理”代码/重命名/重构 | 违反“只写文档不改代码”；重构是独立任务，各自走 HDD |
| 静态通读的结论当事实写总纲 | 未运行验证的口径描述必须标“静态推断，待运行验证” |
| 一次性停工补全所有 QC | 增量策略（随改动补 + 关键数优先）；停工补课通常烂尾 |
| 不问用户就判某产物“废弃” | 废弃判定是口径决策；删掉的结果不可追回 |
| 大爆炸式重命名成 stepN/figN | 新文件用新约定，存量是否迁移由用户拍板（爆炸半径大） |
| 删掉或无视旧 AGENTS.md / CLAUDE.md | 丢失代码里没有的意图资产；两套文档并存漂移——按“验证后继承”处置（见上节） |

## 两路径关键差异

下表逐维度对照两条路径。

| 维度 | 空仓库 | 已有仓库 |
|---|---|---|
| 入口物 | templates/ 直接用 | 模板降级为“应有哪些决策”的检查单，不覆盖现实 |
| 文档-代码时序 | 文档先行，代码跟随 | 文档追认代码现状（考古→对齐→登记） |
| 主要风险 | 跳过设计拍板直接开写 | 凭想象写文档（V5 当事实）；借初始化乱重构 |
| 需求确认重点 | 口径怎么**定** | 现状怎么**认**（现行/废弃/隐含口径显性化） |
| QC/锚点 | 与代码同生 | 补债策略：关键数优先 + 随改动补 |
| 首个交付物 | 骨架 + 设计文档 | 考古报告（diagnosis/，带证据等级） |
| 首份 handoff | “项目初始化” | “纳入框架 + 现状盘点见考古报告” |

注：本框架不依赖 git。项目有 git 时，收口 handoff 必须提交入库：与改动同提交，或紧随其后的独立提交。脚本归档与结果删除都是普通提交。历史由版本库与 handoff 体系双重承载。
