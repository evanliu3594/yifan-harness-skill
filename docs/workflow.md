# 全链工作流：闸门、回退与跨阶段协议

本文是 yifan-harness-skill 的总调度图。它讲三件事：五个阶段如何衔接，每道闸门（gate）放行什么，出问题时退回哪里。各阶段细节见对应 SKILL.md。

## 总图

下图给出五个阶段的先后顺序、闸门位置与回退路径。

```
┌──────────────────────── project-conventions（贯穿全程）────────────────────────┐
│  AGENTS 路标 · 规范文件 · README 信息表 · handoff 交接 · 需求确认 · 去留       │
└──────────────────────────────────────────────────────────────────────────────┘
        ┌─────────┐   G1    ┌─────────┐   G2    ┌─────────┐   G3
        │①计算设计 │ ──────▶ │②代码落地 │ ──────▶ │③验证结果 │ ──────▶ …
        └─────────┘         └─────────┘         └─────────┘
              ▲                   ▲                   │        ┌─────────┐   G4    ┌─────────┐
              │                   │                   └──────▶ │④数据可视 │ ──────▶ │⑤文章写作 │
              │                   │                             └─────────┘         └─────────┘
              └────────── 回退：按问题根因退到对应阶段（见回退路由） ─────────────────▲
```

每个“stepN 落地”内部是 ②→③ 的小循环（HDD：AT Design → DEV → AT Run）。每个研究里程碑做一次 ③ 的全量审计（代码/图件/手稿 ↔ 设计）。

## 设计分级：先定仪式，再开工

开始设计前，先判工作量级别，再决定走多少流程。级别用平常话说，不用代号。先声明级别，用户可覆盖。中途变大就升级。

| 级别 | 判据 | 仪式 | 过哪道闸门 |
|---|---|---|---|
| 快算 | 单点数值、单图、单表；不新增或改动口径 | 声明预期值或预期性质，执行后核对；handoff 一行 | 不走 G1，不进设计文档 |
| 小改 | 一个 step 内的改动、加一张敏感性图、换已拍板口径的呈现方式 | 聊天内确认口径点与预期；设计要点进 handoff | G1 简化 |
| 项目 | 新研究问题、新管线、新数据集、口径变更、要交付论文或报告 | 设计对话 + 设计文档 + 复现者检查 | G1 完整门禁 |

分级细则见 `skills/research-design/references/design-conversation.md`。原则有两条。项目级流程不能拖死快算。快算的轻仪式也不能用来交付项目。

## 闸门表

每道闸门按序放行，未过就停在当前阶段。

| 闸门 | 从 → 到 | 放行条件（上游技能的 Verification Checklist 全过） | 未过的典型代价 |
|---|---|---|---|
| **G1** | 设计 → 代码 | 口径已拍板并登记；项目级含复现者检查；公式链/数据契约/维度速查成文；缺口表分好类 | 代码里发明口径 → 全量返工 |
| **G2** | 代码 → 验证 | HDD 分流判定成文；AT 先于 DEV 锁定且 AT Run 全过；QC 门通过 | 带病结果流入下游 |
| **G3** | 验证 → 可视化/写作 | Blocker 清零；QC 值可复算；问题分类处置完毕；审计报告落 diagnosis/ | 图和论文建立错误数字上 |
| **G4** | 可视化 → 写作 | 双 QA（结构+视觉）过或如实 NOT AUDITABLE；图件清单与代次现行 | 手稿引用过期口径的图 |
| **G5** | 写作 → 投稿 | 数值对账 100%；公式三处同步；术语表一致；Limitations 覆盖缺口表 | 审稿人发现自相矛盾 |

G3 是枢纽闸门：可视化与写作都只准消费**通过验证的现行代次产物**。

## 回退路由（发现问题时退到哪）

发现问题时，按根因退回对应阶段修复。

| 问题类型 | 症状 | 退回阶段 | 动作 |
|---|---|---|---|
| 实现错误 | QC 不过、锚点偏、复算不一致 | ② 代码落地 | 完整 HDD 修复 → 重过 G2/G3 |
| 口径错误/歧义 | 设计与实现脱节、手稿自相矛盾 | ① 计算设计 | 重新拍板 → **三处同步**（设计/代码/手稿）→ 重过全链受影响闸门 |
| 数据/方法固有 | 对齐损失、Σ≠、模型近似 | ③ 验证（登记） | 量化 → 固有缺口表 → Limitations；不改数 |
| 图件口径错 | 图上数值与 output 对不上 | ④ 可视化 | 改 figN 脚本重跑 → 双 QA 重过 |
| 手稿数字错 | 对账表不闭合 | ⑤ 写作（小）或 ②（根因在数） | 先定位数的根因，再改对应层 |

原则：**退到根因所在层修**，不在表象层打补丁。修复后必须重跑受影响的全部下游验证，并在 handoff 记录回退原因与影响面。

## 跨阶段协议

四个协议约束跨阶段动作。

### 口径变更协议（影响全链的改动）

口径变更分六步处理，先停下游。

1. 触发：任何人（用户/审稿/新发现）提出改口径 → 先停下游。
2. 走 ① 的拍板流程（需求确认协议）→ 更新设计文档与契约。
3. 受影响 step 逐个重实现重验证（G2/G3）。
4. **整代重跑**结果与图（④ 的代次管理）。
5. 手稿数值重新对账、公式三处同步（⑤）。
6. handoff 留痕（动机/影响面/新旧行对比）。

### 探索性试算与正式结果的边界

研究常需要先试算一次，看方向对不对。试算不写设计文档，也不锁口径，但必须守四条边界。

1. 开工前声明这是探索性试算，不作正式结果。
2. 产物放 `diagnosis/` 或临时目录，不进 `output/`、`pics/`。
3. 不进手稿、不进汇报，不引用为证据。
4. 想转正就重新分级，走 G1。

登记表放当次 handoff，五列：试算、目的、产物位置、结论用途、是否转正。探索性分析与确证性分析在同一份手稿里分区标注。确证性分析的口径必须先拍板。

### 里程碑全量审计协议

在“结果齐了要动笔/汇报/投稿”前，③ 的审计矩阵四行全跑：代码↔设计、图件↔设计、手稿↔管线、产物↔产物。报告产出到 diagnosis/ 目录。Blocker 清零才进入下一里程碑。

### 交付汇报协议

对外汇报材料（PPT/报告）消费的每一个数字与图，都按 G3/G4 标准执行：现行代次、对账闭合、术语定稿。材料版本与手稿版本的同步关系在 `scripts/README.md` 登记。

## 与单一阶段技能的读法

知道阶段就直接读对应技能，不知道就先定位。

- 先判级。快算直接进入对应阶段。小改在单阶段内确认。项目走完整设计。判级见 `skills/research-design/references/design-conversation.md` 第 4 节。
- 只做一件事时：直接按对应 SKILL.md 执行（其 Verification Checklist 即该阶段闸门）。
- 不知道自己在哪个阶段：看上一个交付物是否过了闸门表。没过就还在上一阶段。
- 接手半途项目时，先经 project-conventions 通读 AGENTS 路标、各目录 README 信息表、规范文件与 handoff/ 最新一份，再定位当前阶段。若该仓库没有这套体系，或体系失真，先走 project-conventions 的初始化程序。已有仓库路径：考古 → 对齐 → 建体系 → 补验证债。之后重新定位阶段。
